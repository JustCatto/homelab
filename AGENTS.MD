# Homelab agent guide

Read `docs/architecture.md`, `docs/structure.md`, `docs/setup.md`, and `docs/deployment.md` before changing infrastructure. These files describe the intended deployment and the real prerequisites; do not assume access to the Proxmox cluster from this workspace.

## Conventions

- `bootstrap/create-debian-template-9000.sh` builds the Debian 13 template once on the Proxmox node (not in Terraform state). It requires the HomeLab SSH public key at `/root/homelab-pubkey.pub` by default; do not overwrite an existing VM ID 9000. If changing template user, storage, or bridge, keep `docs/setup.md`, the Terraform example and the Ansible inventory example aligned.
- Terraform in `terraform/` owns cloned Proxmox resources only. Use `bpg/proxmox`, API-token authentication, cloud-init and named variables; never hardcode secrets, IPs, node names, or public keys in resources. The template stores the HomeLab key by default; Vaultwarden deliberately overrides the clone's cloud-init keys with `vaultwarden_ssh_public_key`. Keep `shared_ssh_public_key` available for other VMs that should use the HomeLab key.
- Ansible is organized by service: `ansible/<service>/` owns that service's playbook, inventory, example variables, static `files/`, and secret-bearing `templates/`. Vaultwarden's host packages, Tailscale enrolment, nftables policy, Fail2ban and Compose deployment live entirely in `ansible/vaultwarden/`. The service-local `ansible.cfg` sets its inventory; `site.yml` loads local `secrets.yml`. Run `ansible-playbook site.yml` from that directory after creating the ignored local files. Keep future services self-contained in their own folders.
- Docker Compose owns the application containers. Keep Vaultwarden private to the Docker network, run it as UID/GID 1000, preserve the `/data` bind mount, and bind Caddy HTTPS only to the assigned Tailscale IPv4. Caddy uses an internal CA; client trust is an explicit setup step. Do not publish this service via NPM.
- Preserve least privilege: restrict capabilities, read-only root filesystems and secret file permissions; do not add the SSH user to the `docker` group (membership grants effective root access). Tailscale enrolment must precede any restrictive firewall or Compose binding. Never log the Headscale pre-authentication key. Replace only the service-owned `inet vaultwarden_firewall` table, never flush the global nftables ruleset. Protect Docker-published ports in FORWARD as well as INPUT; retain LAN SSH recovery and Proxmox console access. Fail2ban protects host SSH; it does not protect Vaultwarden logins.
- Never commit real `*.tfvars`, Terraform state/plans, `ansible/<service>/inventory.ini`, `ansible/<service>/secrets.yml`, or the deployed `.env`. Avoid printing secrets in task output. Keep the public SSH key configurable even though it is not secret.
- Keep versions explicit and update them deliberately with release notes and a backup. Avoid unrelated refactors when making deployment changes. Update the docs and examples when changing parameters, prerequisites, or procedures.

## Validation

Run `terraform fmt -check -recursive` and `terraform validate` from `terraform/` after `terraform init -backend=false` (initialization downloads a provider). Run `ansible-playbook --syntax-check site.yml` from `ansible/vaultwarden/` after creating its ignored inventory and secrets files. Run `docker compose --env-file <local-env> -f ansible/vaultwarden/files/compose.yaml config` with non-secret test values. Apply/upgrade only when authorized with working credentials; a successful syntax check does not prove a live deployment. See `docs/deployment.md` for post-deployment checks and backup/restore.
