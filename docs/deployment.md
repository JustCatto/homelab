# Deployment and operations

## Apply and verify

From the repository root, run `terraform -chdir=terraform fmt -check -recursive` and `terraform -chdir=terraform validate` after `terraform -chdir=terraform init`. Review `terraform -chdir=terraform plan` before `apply`; VM/template ID mismatches and disk changes may replace resources. Then enter `ansible/vaultwarden/` and run `ansible-playbook site.yml` (after creating the untracked `inventory.ini` and `secrets.yml` with `headscale_url` and `headscale_auth_key`). Check `tailscale status` and `tailscale ip -4` on the VM; verify `vaultwarden-firewall.service` and `sudo nft list table inet vaultwarden_firewall`. Check `sudo docker compose --env-file .env -f compose.yaml ps` in `/opt/vaultwarden`, `sudo journalctl -u fail2ban` and `sudo fail2ban-client status sshd`. Install the Caddy internal root CA on enrolled clients, ensure private DNS resolves the hostname to the Tailscale IPv4, then open `https://<vaultwarden_domain>` and verify the certificate, login and disabled registration. A fresh install has no accounts: arrange first-user onboarding before relying on the service. If temporarily enabling signups to create the first account, restrict access to the site at the upstream firewall first, set `SIGNUPS_ALLOWED` to `true` only for that short window, then restore `false`, rerun Ansible and confirm registration is closed. Do not leave public registration enabled. If HTTPS fails, check Headscale connectivity, private DNS, internal CA trust and `sudo docker compose logs caddy` in that directory. Public HTTP-01 is not used. Do not paste logs containing credentials into issue trackers.

Ansible reconciles Compose when managed files or the startup unit change, and a boot-time systemd unit waits for Tailscale before starting the stack; unchanged containers are not recreated. If containers are manually stopped without changing managed files, restart `vaultwarden-compose.service` on the VM. The admin token is in a root-owned `0600` env file and is available to Docker/host root; avoid granting other users Docker access. The Vaultwarden process uses UID/GID 1000, a read-only root filesystem, no added Linux capabilities, `no-new-privileges`, and limited PIDs. Only `/data` and a temporary `/tmp` are writable. Caddy publishes only TCP 443 on the VM's Tailscale IPv4 and retains its internal CA (including a sensitive signing key) in named volumes. Protect the CA key and distribute only the root certificate to clients. Docker image tags are explicitly pinned, not immutable digests: verify image provenance, scan releases and upgrade the pins deliberately.

## Upgrades and recovery

Before upgrading images or changing VM disks, take a consistent backup of `/opt/vaultwarden/data` (including the SQLite database, attachments and keys), the Docker Caddy volumes (`caddy_data`, `caddy_config` under the Compose project), and the untracked deployment settings; securely protect backups and test restore on an isolated host. For a consistent SQLite copy, stop the Vaultwarden service briefly or use SQLite's online backup mechanism; do not blindly copy a live database. Preserve Caddy's internal CA state when restoring so clients continue to trust issued certificates; re-creating the CA requires distributing its new root certificate to every client. Keep Proxmox VM backups and Terraform state backups separately. Backups containing Vaultwarden data or admin tokens are sensitive.

Update image tags in `ansible/vaultwarden/files/compose.yaml` (and the hash-generation command in `docs/setup.md`), review upstream release notes, run Ansible, and verify logs/HTTPS. Changes to the domain also require updating DNS and the Ansible secret vars. Restore data ownership to UID/GID 1000 (mode 0700 for the directory) before restarting. Avoid `terraform destroy` unless the VM and all its data are intended to be removed. Fail2ban protects only SSH; for application login rate limiting, add a tested Vaultwarden-aware filter or edge protection rather than assuming the host jail covers containers. Vaultwarden is available through Headscale rather than NPM. The firewall permits LAN SSH recovery but not LAN HTTPS; validate that LAN port 443 is blocked even when addressed to the Tailscale IPv4, and test HTTPS from a Headscale client. If a firewall change breaks networking, recover through the Proxmox console; do not flush the Docker/Tailscale ruleset. Re-enrolling a lost Tailscale node requires a fresh valid Headscale pre-authentication key.
