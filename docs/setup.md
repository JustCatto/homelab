# Initial setup

## Prerequisites

Install Terraform >= 1.6, Ansible, and an SSH client locally. You need root access to the target Proxmox node once to build the Debian 13 template, and access to the Proxmox VE API to clone it. The VM network bridge needs DHCP, outbound access to Headscale, Debian/Docker repositories and image registries, and DNS. Verify that the Proxmox datastore supports VM disks and cloud-init. Select unused template ID 9001 on proxmox1 and 9002 on proxmox2, and a different, unused ID for the application VM. The Terraform output for IP addresses requires a running guest agent; if absent, check the DHCP lease/Proxmox console.

Create a dedicated Proxmox API user/token with privilege separation enabled and narrowly scoped permissions for cloning/allocating/configuring/powering VMs on the chosen node, reading the template, and using the datastore and bridge. Exact required privileges vary by Proxmox version/provider operations; consult the bpg/proxmox provider permissions documentation and test against your cluster. Do not use a root password. Use a valid API TLS certificate where possible; `proxmox_insecure = true` bypasses certificate verification and should only be a temporary exception. Confirm whether the API is reachable at port 8006 or through your reverse proxy on 443; the UI fragment is not part of the API URL.

## Build the Debian 13 template (once per Proxmox node)

For a standalone walkthrough, see [`bootstrap/README.md`](../bootstrap/README.md). `bootstrap/create-debian-template-9000.sh` follows the Proxmox `qm` workflow shown in the setup notes: download `debian-13-generic-amd64.qcow2` from the Debian **trixie/latest** cloud images, create the selected VM template (`debian-13-template`, 2 GiB RAM, 2 cores, virtio NIC on `vmbr0`), import its `scsi0` disk into `local-lvm`, add a cloud-init drive, set the boot disk, SCSI controller and serial console, configure DHCP and the guest agent, set the cloud-init user to `catto`, then convert the VM to a template. The script also downloads Debian's `SHA512SUMS` over HTTPS and verifies the image and installs `qemu-guest-agent` **inside the image** using `virt-customize` before importing it. The checksum file is fetched from the same HTTPS origin; it is not independently signature-verified. `trixie/latest` can change over time, so record the image build/date when creating or replacing a template.

Run the script **on the Proxmox node as root**, not on your workstation or in the Vaultwarden VM. First install the host-side tools if absent: `apt-get update && apt-get install -y wget libguestfs-tools`. Place the **HomeLab public key** (not its private key) on the Proxmox node at `/root/homelab-pubkey.pub`, as in the original `qm set <template-id> --sshkeys /root/homelab-pubkey.pub` step. Copy `bootstrap/create-debian-template-9000.sh` to the node (for example under `/root/`), then run `VM_ID=9001 bash /root/create-debian-template-9000.sh` on proxmox1 or `VM_ID=9002 bash /root/create-debian-template-9000.sh` on proxmox2. The script requires a nonempty public key file and configures it as the template's default cloud-init SSH key; set `SSH_PUBLIC_KEY_FILE` if the file is stored elsewhere. The Proxmox node needs internet access and sufficient free space in `/var/tmp` for the downloaded image; `TMPDIR` can point to another filesystem. You can set `STORAGE` (default `local-lvm`), `BRIDGE` (default `vmbr0`), or `TEMPLATE_USER` (default `catto`) in the script's environment if your node differs. Verify the resulting template, disk, cloud-init drive and agent settings in Proxmox before cloning. The script refuses to change an existing VM ID and **does not** automatically destroy partially created VMs on failure; inspect any partial VM before retrying.

The template has the stored HomeLab public key as its default cloud-init `sshkeys`. **Vaultwarden uses a separate key:** Terraform sets `vaultwarden_ssh_public_key` on the cloned VM and replaces that clone's template-level cloud-init `sshkeys` value; it does not append to the HomeLab key. `shared_ssh_public_key` records the HomeLab key for future VMs but is not automatically copied to the template by Terraform. Keep the Vaultwarden private key only on your trusted SSH client. The template user, Terraform `vm_admin_user`, and Ansible `ansible_user` must match (`catto` by default). Changing the template user or storage requires updating `terraform/terraform.tfvars` and the service inventory accordingly. The Debian image's cloud-init user must have working sudo on the cloned VM; verify SSH and sudo before running Ansible.

## Local configuration

1. Copy `terraform/terraform.tfvars.example` to `terraform/terraform.tfvars`; set node, template IDs (`proxmox1_debian_template_vm_id = 9001` and `proxmox2_debian_template_vm_id = 9002`), datastore, bridge, unique VM ID, and **both public keys**: `shared_ssh_public_key` matching the HomeLab key stored on the templates, and `vaultwarden_ssh_public_key` for this VM's SSH access. The Vaultwarden-specific key overrides the template's cloud-init key setting in the clone; configure your SSH client to use its matching private key. Reuse `shared_ssh_public_key` in future VMs where appropriate. Never paste either SSH private key into a tfvars file. Override `proxmox_endpoint`, `vm_admin_user`, or VM sizing if needed; for the bootstrap defaults leave `vm_admin_user = "catto"` and `proxmox_datastore_id = "local-lvm"`. Protect local Terraform state and any remote state backend.
2. Set `TF_VAR_proxmox_api_token` in your local shell/secret manager to a `user@realm!tokenid=secret` value. Avoid shell history and CI logs. An ignored tfvars token is an alternative, not the preferred path. The token can still appear in plans/logs: keep them private.
3. Run `terraform -chdir=terraform init`, `terraform -chdir=terraform plan` and, after reviewing the plan, `terraform -chdir=terraform apply`. Terraform does not create the Debian template (the bootstrap script does) or DNS records.
4. Get the VM's IP from `terraform -chdir=terraform output vaultwarden_ipv4_addresses` or DHCP. Copy `ansible/vaultwarden/inventory.ini.example` to ignored `ansible/vaultwarden/inventory.ini` and replace `REPLACE_WITH_VM_IP` (and user if needed). Test SSH key login and sudo.
5. Generate a valid pre-authentication key in your existing Headscale instance. Ensure the VM trusts Headscale's HTTPS certificate and has outbound network access to Headscale, package registries and DERP relays. No public ingress or NPM forwarding is required. `vaultwarden_domain` must resolve on Headscale clients to the VM's actual Tailscale IPv4 (private/Headscale DNS or client hosts entries). The hostname must belong to a publicly authoritative Cloudflare zone for DNS-01 certificate issuance; client DNS should resolve it to the VM's Tailscale IPv4. No public HTTP/HTTPS port forwarding is required. The VM needs outbound access to Cloudflare, the ACME CA and Go modules/Docker registries to build the pinned Cloudflare-enabled Caddy image. Keep Proxmox console access for recovery.
6. Generate a strong admin password and hash it with the **same** Vaultwarden image version as Compose: `docker run --rm -it vaultwarden/server:1.37.4 /vaultwarden hash` (run on a trusted Docker host). Copy `ansible/vaultwarden/secrets.yml.example` to ignored `ansible/vaultwarden/secrets.yml`, set `vaultwarden_domain` (hostname only), the complete resulting `$argon2id$...` hash, `headscale_url` (HTTPS control URL), `headscale_auth_key` (pre-authentication key) and `cloudflare_dns_api_token` (zone-scoped Zone:Read/DNS:Edit token). Store the original password securely; the hash is still a credential to protect. To avoid plaintext in shell history, use the image's interactive hash prompt.
7. From the repository root, run `cd ansible/vaultwarden`, then `ansible-playbook site.yml`. The service-local `ansible.cfg` selects `inventory.ini`, and the playbook loads `secrets.yml` automatically. Both files must exist locally but remain untracked. The cloud-image user must be able to sudo (add `--ask-become-pass` if required). This installs Tailscale from its official Debian repository, joins Headscale, installs Docker, starts host SSH Fail2ban, validates/applies nftables rules and reconciles Compose. It keeps SSH reachable from `192.168.1.0/24` during migration; after enrolment you may change the inventory host to the VM's Tailscale IPv4.

The node, private DNS mapping, Headscale URL and credentials cannot be derived from the repository or the browser URL. Never commit populated local configuration or passwords.
